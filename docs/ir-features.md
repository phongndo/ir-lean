# IR features

Everything the pinned LLVM IR can contain, each item modeled, refused or assumed, and a test that the emitter does
what each item's class says. This is SEM-08 in the [task list](llvm-verification-tasks.md), and the first half of
[Phase 0B](roadmap.md#phase-0-semantic-fidelity-and-trust-infrastructure)'s exit criterion. For what any theorem
means, read [trust](trust.md) first. Facts here were checked on 2026-11-09 at LLVM `llvmorg-23.1.3`.

**This is a map, not a semantics.** A modeled item has a meaning in `IRLean`; how well that meaning matches LLVM is
what the rest of the tests are for. The classification says what the emitter does with each item, and checks it.

## The classes

| Class | Means |
| --- | --- |
| Modeled | `IRLean` gives it LLVM's meaning: computed, or checked on each run, as LangRef at the pin says |
| Assumed | Translated, and the model ignores it. The reason says why that's right: it only guides optimization, lowering or tools, such as `cold` or `!prof`, or it can't be broken in the model. A few are assumptions a theorem rests on, listed [below](#assumptions-it-names) |
| Refused | The emitter refuses any function containing it, so no theorem is about one |

A refused item is refused whatever it means, so refusing is always sound. What it costs is coverage.

## What the check does

`tests/ir_features.py check`, the `ir_features` test, in about 35 s:

1. Derives the items again from the pinned source, classifies them, and fails if the file differs. So an LLVM bump that
   adds an intrinsic, an attribute or a metadata kind fails until it's classified.
2. Fails if an item has no rule, or two. Rules name modeled and assumed items one by one; only refused items can be
   matched by a prefix, such as `llvm.nvvm.`, so nothing new is modeled or assumed without someone naming it.
3. Builds a probe of each item, a small module using it, and runs the emitter on it. A modeled or assumed item has
   to translate, and a refused one has to be refused. Intrinsics are probed by `build/ir-lean-probe`, from
   [`src/Probe.cpp`](../src/Probe.cpp), which builds a call to each from LLVM's own type tables: one for each shape of an
   overloaded intrinsic's first type, integer, vector, scalable vector, floating point and pointer, and every call
   passes LLVM's verifier. The rest are in [`tests/ir_features/probes.ll`](../tests/ir_features/probes.ll), or built
   from templates in the script. A modeled intrinsic may be refused at some shapes only because of an item that's
   refused itself, such as a scalable vector type. A probe the emitter crashes on, or gives no report for, fails,
   and so does an item with no probe it reads, unless the script lists it with its reason, [below](#what-it-doesnt-show).
4. Elaborates, in one Lean process, the Lean the emitter prints for every probe it translates. Reporting a function
   translated isn't enough: the Lean has to typecheck.
5. Checks each modeled intrinsic has a case in the emitter's `emitIntrinsic`, and each case there is classified.

`ir_features_rules`, `tests/ir_features_test.py`, tests the rules without LLVM: an unclassified item, two rules,
a modeled or assumed prefix, a rule naming what the pin lacks and an unknown reason each fail.

On 2026-11-09, four changes to the emitter each failed the check: removing `ctpop`'s case, adding a case for an x86
intrinsic, accepting `nocallback`, and dropping an item's line from the file.

## What it found

The first run, on 2026-11-09, found three things the emitter did wrong, now fixed:

- **A call whose calling convention isn't the callee's translated as an ordinary call.** LangRef says "The calling
  convention of any pair of dynamic caller/callee must match, or the behavior of the program is undefined", so the
  model had less undefined behavior than LLVM there, which is unsound for a safety proof and for the target of a
  refinement. It's refused now, and so is a call through a pointer that could reach a function with another one.
  InstCombine replaces such a call with `store i1 true, ptr poison`, its mark for code that can't run, unless it
  counts one of the two conventions as compatible with C's.
- **Vector forms of 16 integer intrinsics were reported translated, and printed Lean that doesn't elaborate:**
  `ctpop`, `ctlz`, `cttz`, `abs`, `bswap`, `bitreverse`, `fshl`, `fshr`, `ucmp`, `scmp`, and the six
  `*.with.overflow`. Each printed the scalar operation applied to a vector. Lean rejected them, so no proof was wrong,
  but a pair with one counted as translated and then failed. They were refused at first, and now they're modeled
  lane by lane, in [`IRLean/Lanes.lean`](../IRLean/Lanes.lean), checked by `vecopcheck` against Alive2 and LLVM's
  constant folder.
- **`llvm.memcpy` and `llvm.memset` with a length narrower than 64 bits printed Lean that doesn't elaborate.** The
  length is zero-extended now, as LangRef's unsigned length is.

Going through what the emitter refuses in InstCombine's tests found three more:

- **The emitter crashed on 36 of the pairs.** On a vector-typed constant expression, such as a `bitcast` of a
  constant vector, `constant` read an element that isn't there, and segfaulted. On a `getelementptr` over a
  scalable type, it asked LLVM for a fixed size, and aborted. Both are refused now, as the forms
  `vector-constant-expression` and `getelementptr-over-a-scalable-type`, and the check fails if the emitter crashes
  on any probe.
- **`noundef` on a struct** was reported translated, and printed Lean that doesn't elaborate. It's modeled now, as
  `noundef` on a vector is: a poison field or lane anywhere is undefined, as LangRef's "any undefined or poison bits"
  says.

## Assumptions it names

Most assumed items are hints. These are what a theorem rests on, and [trust](trust.md#known-gaps-in-the-model) lists
them:

- **`tail` and `musttail` calls** also promise the callee doesn't touch the caller's allocas, which the model doesn't
  check. A function without memory has none.
- **String attributes on parameters and return values** are ignored. LangRef gives string attributes no meaning, and
  targets read them as settings.
- **`!absolute_symbol`** narrows where a symbol is. The emitter doesn't read metadata on functions and globals, and a
  theorem holds for every address the model allows, which includes the ones it allows.
- **Calling conventions** are ignored where caller and callee agree, since they only say how values are passed.

## Updating it

After changing a rule, or what the emitter accepts, run `nix develop -c tests/ir_features.py generate` and commit the
file with the change. The check fails until they agree, which is the point: a change to what the emitter accepts is
a change to the classification, and shows in review as lines of the file.

`tests/ir_features.py summary` prints the totals from the file, without LLVM.

## What it doesn't show

- **That a modeled item is modeled right.** The probes show the emitter translates it and Lean accepts what it prints.
  Whether that matches LLVM is what `opcheck`, `gepcheck`, `x86check`, the differential tests and Alive2 are for.
- **Every way an item can appear.** A probe uses an item once, in one place, at one type or a few. An attribute is
  probed on `i32`, a pointer and a vector, and a form is listed only where the emitter treats it differently.
- **134 items have no probe.** 117 are intrinsics no call the generator builds passes LLVM's verifier, such as
  `llvm.experimental.gc.statepoint`. Each is refused, and has no case in `emitIntrinsic`, so the emitter's default
  refuses it, which the check confirms for each. The other 17 are listed in the script's `UNPROBEABLE`, each with why
  no IR the emitter reads can hold it, such as `UserOp1`, internal to LLVM's passes, or `elementtype` on a
  definition's parameter, which the verifier rejects. One, `jumptable` at a call, has IR that can hold it, but LLVM
  23.1.3's verifier checks it with `cast<GlobalValue>(V)->hasGlobalUnnamedAddr()`, where `V` is the call, so it
  reads bits that aren't the call's, and whether a probe passes changed from run to run on macOS. The emitter refuses
  it, having no case for it in `checkFunctionAttributes`. All are refused but three: `immarg`, at two places, goes only
  on an intrinsic's declaration, where LLVM's verifier checks it, and the `metadata` type is only an operand of an
  intrinsic, and the emitter translates none that takes one.
